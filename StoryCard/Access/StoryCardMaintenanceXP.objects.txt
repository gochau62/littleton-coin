Story Card Maintenance - contents of StoryCardMaintenanceXP.mdb
================================================================

Access file format JET4 (Access 2000/XP .mdb), 940 KB.
Database title "Story Card Maintenance", company "Littleton Coin Company",
author "Network Administrator".  VBA project name "Story Card Maintenance".


LINKED TABLES (ODBC, Connect string "DSN=AS400;")
-------------------------------------------------
Every table except side1 is a link to the iSeries.  Nothing is stored in the
.mdb itself - the file is only a front end.

LSCPRDLIB/IVSCBODYP        story card body text, one row per printed line
    SCBSKU   CHAR(10)      item number (= ITMMSTP.IISKU#)
    SCBLNO   DECIMAL(4,0)  line number, 1-12 side 1, 13-22 side 2
    SCBTXT   CHAR(50)      the printed line
    SCBSRK   CHAR(15)      search key, the same value on every line of a card
    unique key (SCBSKU, SCBLNO)

LSCPRDLIB/IVSCFOOTP        the shared footer that prints on every story card
    SCFSKY   DECIMAL(7,0)  footer key, only key 1 is ever used
    SCFLNO   DECIMAL(4,0)  line number
    SCFTXT   CHAR(50)      the printed line
    unique key (SCFSKY, SCFLNO)

LSCPRDLIB/ITMMSTL1         item master logical, 80 columns, read only here.
                           Only IISKU# and IIDESC are used - to prove a SKU
                           exists and to show its description.

LSCPRDLIB/ITMEXPDSCP       extended item description.  Linked but never read
                           by any form; only Query1 below touches it.

(Column widths above are the real Db2 widths, read back out of the link's
 RmtInfoLong blob.  Access stores JET4 text lengths in bytes, so the schema
 it reports - 20/100/30 - is twice the character count.)

           scratch table from whoever built the original screen.

                   a Select button (Command12) and an Exit button (Command1,

BodyMaintenance    the working screen.
    Image0         C:\Story Card Maintenance\LCC_Logo.bmp
    Label1         "Story Card Maintenance"
    Combo1         SKU picker, row source
                   SELECT DISTINCT IVSCBODYP.SCBSKU, ITMMSTL1.IIDESC
                     FROM IVSCBODYP INNER JOIN ITMMSTL1
                       ON IVSCBODYP.SCBSKU = ITMMSTL1.IISKU#

                   (so only SKUs that already have a card are listed)

    Text13         footer text, read only preview

                   Text11 (10) and Text13 (2)

    Command1       Save

HOW A SAVE WORKS TODAY (Form_BodyMaintenance.Command1_Click)
-------------------------------------------------------------
1.  Read Text9, Text11, Text36 and Combo1 straight off the form.
2.  CheckSku - SELECT COUNT(*) FROM ITMMSTL1 WHERE IISKU# = the SKU.
3.  DetermineMode - COUNT(*) on IVSCBODYP for the SKU decides insert or update.
4.  Walk the text a character at a time looking for Chr(13), and for each
    chunk build an INSERT or an UPDATE by string concatenation and run it
    through dbHead.Execute.  Side 1 numbers from 1, side 2 from 13.
5.  In update mode, CheckLineMode runs a COUNT(*) per line to decide UPDATE
    vs INSERT, so a 22 line card costs 22 extra round trips.
6.  Afterwards UpdateBlank blanks lines from wherever side 2 stopped up to 21.

Known defects in that code, carried into this note so they are not
reproduced by accident:

  * Off by one on both sides.  The guards are "intSCBLno <= 11" and
    "intSCBLno <= 21", but the rulers and the reload query say 12 and 22.
    Line 12 and line 22 can never be saved.
  * The tidy-up loop runs "For intLine = intSCBLno To 21", so line 22 is
    never blanked either.
  * Only side 2 is tidied.  Shorten side 1 from eight lines to three and
    lines four to eight keep their old text forever.
  * The message text disagrees with the code - it says "maximum number of
    lines (9) for side 2" while the ruler shows 10.
  * Every value is concatenated into the SQL string, so an apostrophe in the
    text breaks the statement.  Side 1 and side 2 wrap the text in double
    quotes, the footer screen wraps it in single quotes, so the two screens
    fail on different characters.
  * There is no transaction.  A failure on line 7 of 22 leaves the card half
    written with no way back.
  * FootMaintenance never clears lines.  Shorten the footer and the extra
    lines keep their old text in IVSCFOOTP and go on printing.
  * DetermineMode is called twice per save and CheckSku twice more, each one
    a separate ODBC round trip.

The replacement in ../Db2 and ../Web fixes all of the above; the line limits
are honoured as 1-12 and 13-22, every value is bound as a parameter, and a
failed save is rolled back to the card as it was.

One thing the replacement deliberately does NOT add: a delete.  Counting the
SQL in the VBA above gives 18 INSERT, 17 SELECT and 12 UPDATE and no DELETE
of any kind - the Access screens never removed a record in their life, and
the only way to retire a card was to blank its lines.  The replacement keeps
that exactly: STYCRD003S blanks, and there is no procedure, no ajax action
and no button anywhere that deletes a row from IVSCBODYP or IVSCFOOTP.
